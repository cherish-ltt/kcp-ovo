# KCP 流模式（Stream Mode）— 实施计划

## 概述

在 KCP 底层核心（`core/kcp.rs`）和配置模块（`config/params.rs`）中实现完整流模式。流模式下：send() 将大消息按 MSS 切分为多个 segment，**所有 segment 的 frg 均设为 0**，不再受 255 分片上限约束；recv() 一次性拼接 `rcv_queue` 中所有可读 segment 的字节并交付，无消息边界；peeksize() 仅返回第一个 segment 的大小。流模式与非流模式不能互连互通。

## 设计决策（来自设计评审）

| 问题 | 决策 |
|------|------|
| 流模式定义 | 底层 `core/kcp.rs` 中实现，send() 所有分片 frg=0，recv() 连续拼接 |
| 255 分片限制 | 流模式下移除 `count > u8::MAX` 检查 |
| send() 签名 | 保持 `fn send(&mut self, data: &[u8]) -> KcpResult<usize>` 不变 |
| recv() 签名 | 保持 `fn recv(&mut self) -> KcpResult<Bytes>` 不变 |
| peeksize() | 流模式下仅返回第一个 segment 大小，不等待 frg 组装 |
| 开关方式 | `KcpConfig` 中新增 `pub stream_mode: bool`，默认 false |
| frg 设置 | 所有分片 frg=0 |
| recv 策略 | 一次性读取所有可用 segment 并拼接 |
| input() 条件 | 不改变，sn 连续即可移入 rcv_queue |
| 窗口管理 | 不改变 |
| 互连 | 不能互连（frg 语义不同） |
| 便捷构造 | 新增 `KcpConfig::stream_mode()` |
| 帧标记 | 不加入，无边界字节流 |

## 实施步骤

### 步骤 1：KcpConfig 新增 `stream_mode` 字段和构造方法

- **前置条件**：无
- **改动文件**：`src/config/params.rs`
- **改动内容**：
  1. 在 `KcpConfig` 结构体的字段末尾新增：
     ```rust
     /// 是否启用流模式
     ///
     /// true: 流模式，无消息边界，所有分片 frg=0，无 255 分片上限
     /// false: 默认模式，按 frg 链组装消息
     /// 默认值：false
     pub stream_mode: bool,
     ```
  2. 在 `Default for KcpConfig` 的 `Self { ... }` 中添加 `stream_mode: false`
  3. 在 `KcpConfig::fast_mode()` 中添加 `stream_mode: false`
  4. 在 `KcpConfig::normal_mode()` 中（无变化，已通过 default）
  5. 新增方法：
     ```rust
     /// 创建流模式配置
     ///
     /// 流模式下：大消息无 255 分片限制，所有分片 frg=0，
     /// 接收端按 sn 顺序连续拼接，无消息边界。
     /// 默认使用 nodelay=true, interval=20 的低延迟参数。
     pub fn stream_mode() -> Self {
         Self {
             mtu: 1400,
             interval: 20,
             nodelay: true,
             fastresend: 2,
             nocwnd: true,
             snd_wnd: 32,
             rcv_wnd: 128,
             stream_mode: true,
         }
     }
     ```
- **验证方式**：运行 `cargo test --lib config::params::tests` 确认现有测试通过，手动确认新增字段默认行为正确

### 步骤 3：修改 `Kcp::send()` — 流模式分支

- **前置条件**：步骤 2 完成
- **改动文件**：`src/core/kcp.rs`，`send()` 方法
- **改动内容**：
  1. 在 `send()` 方法中，计算 `count` 之后立即加入流模式分支：
     ```rust
     // 流模式下：所有分片 frg=0，无分片数量上限
     // 非流模式：使用 frg 链，有 255 分片上限
     let is_stream = self.stream_mode;
     ```
  2. 将 `if count > u8::MAX as usize { return Err(...) }` 包裹在 `if !is_stream` 条件中：
     ```rust
     // 非流模式下，由 frg 类型决定最大分片大小
     if !is_stream && count > u8::MAX as usize {
         return Err(KcpError::InvalidConfig(format!(
             "Too many fragments, data-size={}byte, allow-max-size={}byte",
             buffer.len(),
             (u8::MAX as usize) * (self.mss as usize)
         )));
     }
     ```
  3. 修改分片循环中的 frg 计算逻辑：
     ```rust
     // 非流模式：frg 使用递减链（最后一个分片 frg=0）
     // 流模式：所有分片 frg=0
     let frg = if is_stream {
         0
     } else {
         (count.saturating_sub(i).saturating_sub(1)) as u8
     };
     let header = KcpPacketHeader::new(
         self.conv,
         crate::KcpCmd::Push,
         frg,
         ...
     );
     ```
- **验证方式**：
  - 非流模式回退测试：`cargo build` 通过，现有测试不受影响
  - 流模式下发送大消息（> 255 分片）不再报错

### 步骤 4：修改 `Kcp::peeksize()` — 流模式分支

- **前置条件**：步骤 2 完成
- **改动文件**：`src/core/kcp.rs`，`peeksize()` 方法
- **改动内容**：
  1. 在方法开头获取流模式标志
  2. 在 `if first.kcp_packet.header.frg == 0` 之前添加流模式短路分支：
     ```rust
     // 流模式下：只返回第一个 segment 的大小，不等待 frg 组装
     if self.stream_mode {
         return Ok(first.kcp_packet.header.len as usize);
     }
     ```
  3. 注意：这段代码应放在获取 `first` 之后、`if frg == 0` 之前，因为流模式下无论 frg 值如何，都直接返回第一个 segment 大小
- **验证方式**：`cargo test` 通过

### 步骤 5：修改 `Kcp::recv()` — 流模式分支

- **前置条件**：步骤 2、4 完成
- **改动文件**：`src/core/kcp.rs`，`recv()` 方法
- **改动内容**：
  1. 修改 `recv()` 开头的 `peeksize` 调用——流模式下 peeksize 返回第一个 segment 大小，但 recv 需要全部读取。因此流模式下不依赖 peeksize 的结果来分配缓冲区大小，而是直接读取所有 segment。
  2. 修改核心读取循环，流模式下不再检查 `frg == 0` 作为终止条件，改为读取全部可用 segment：
     ```rust
     pub fn recv(&mut self) -> KcpResult<Bytes> {
         // 流模式下：读取所有可读 segment
         if self.stream_mode {
             if self.rcv_queue.is_empty() {
                 return Err(KcpError::QueueEmpty);
             }
             
             let mut buf = BytesMut::new();
             // 读取 rcv_queue 中所有 segment
             while let Some(seg) = self.rcv_queue.pop_front() {
                 buf.extend_from_slice(&seg.get_data());
                 self.nrcv_que -= 1;
             }
             
             // 将 rcv_buf 中有序的段移入 rcv_queue
             self.move_rcv_buf_to_queue();
             
             // 快速恢复
             if self.nrcv_que < self.rcv_wnd as usize {
                 self.probe |= IKCP_ASK_TELL;
             }
             
             return Ok(buf.copy_to_bytes(buf.len()));
         }
         
         // 原非流模式逻辑（保留不变）
         let peeksize = self.peeksize()?;
         let mut buf = BytesMut::with_capacity(peeksize);
         while let Some(seg) = self.rcv_queue.pop_front() {
             buf.extend_from_slice(&seg.get_data());
             self.nrcv_que -= 1;
             if seg.kcp_packet.header.frg == 0 {
                 break;
             }
         }
         
         // 后续逻辑...（原样保留）
     }
     ```
  3. 提取 `move_rcv_buf_to_queue()` 辅助方法，避免流模式和非流模式重复代码：
     ```rust
     /// 将 rcv_buf 中有序的段移入 rcv_queue
     #[inline]
     fn move_rcv_buf_to_queue(&mut self) {
         while !self.rcv_buf.is_empty() {
             let front_sn = self.rcv_buf.front().unwrap().kcp_packet.header.sn;
             if front_sn == self.rcv_nxt && self.nrcv_que < self.rcv_wnd as usize {
                 let seg = self.rcv_buf.pop_front().unwrap();
                 self.nrcv_buf -= 1;
                 self.rcv_queue.push_back(seg);
                 self.nrcv_que += 1;
                 self.rcv_nxt = self.rcv_nxt.wrapping_add(1);
             } else {
                 break;
             }
         }
     }
     ```
  > **说明**：提取 `move_rcv_buf_to_queue()` 是保持代码不重复的合理抽象，仍然属于功能实现的核心逻辑而非无谓重构。

- **验证方式**：`cargo test` 通过；流模式下 recv 正确拼接所有 segment

## 注意事项

1. **互连问题**：流模式改变了对 frg 字段的解释方式。发送端所有分片 frg=0，非流模式接收端会将其视为最后一个分片（看起来像一个完整的短消息），从而丢失后续数据。反之，流模式接收端期望所有 frg=0，非流发送端的 frg 链会让接收端意外终止读取。**两端的 stream_mode 必须一致**。

2. **性能考虑**：流模式下 recv 一次性读取所有 segment，对大消息这是合理的。但如果每次只写入少量数据就频繁调用 recv，可能会在 rcv_queue 中积累很多 segment。但这是用户层调用模式的问题，核心逻辑不做优化假设。

3. **peeksize 变更影响**：流模式下 peeksize 返回第一个 segment 大小，不是完整消息大小。如果上层依赖 peeksize 分配缓冲区，需要注意这个行为差异。

4. **stream.rs 不受影响**：根据设计评审决定，`src/stream.rs` 中 `KcpStream` 和 `KcpListener` 不修改。它们使用 `KcpConfig::fast_mode()` 创建 Kcp 实例，stream_mode 默认为 false。如果用户需要流模式，需修改 stream.rs 或自行传递 `KcpConfig::stream_mode()`——但这属于后续功能扩展。

5. **禁止变更**：不修改 `src/error.rs`、`src/packet.rs`（即 `helper/packet.rs`）、`src/queue/`、`src/stream.rs`。

6. **公共 API**：`KcpConfig` 新增 `stream_mode: bool` 字段和 `stream_mode()` 方法是唯一的外部可见变化。`Kcp` 结构体的 `stream_mode` 字段是 `pub` 的（与现有字段风格一致，如 `pub nodelay: bool`），这允许用户在实例创建后查看其流模式状态。
