## 2. 严重问题 (Critical)

### [C1] `test_stream_mode_full_cycle_large_data` 测试断言逻辑缺陷 — 可能漏测数据不一致

**文件**：`src/core/kcp.rs:1400-1415`  
**严重等级**：**CRITICAL**

测试 `test_stream_mode_full_cycle_large_data` 的核心断言逻辑存在缺陷：

```rust
// 验证接收到的数据是原始数据的前缀（因为 rcv_wnd 限制）
assert_eq!(&big_msg[..recv_data.len()], &recv_data[..], "数据内容应一致");
```

**问题 1**：如果 `recv()` 因为 `rcv_queue` 中没有连续 sn 的数据而返回空数据之外的任何数据，但数据的**顺序是不正确的**（例如乱序拼接），该断言只能验证前缀匹配。由于流模式下 recv 一次性弹出所有 segment，如果 rcv_queue 中的 segment 顺序有误（例如 sn=2 在 sn=1 之前），拼接结果会出错，但前缀断言无法发现。

**问题 2**：测试中如果 `recv_result` 是 `Err`，测试只会通过 `if let Ok(recv_data) = recv_result` 分支从而**静默跳过**核心验证。下面是关键代码段：

```rust
let recv_result = receiver_guard.recv();
// 即使不能完全交付（窗口限制），至少流模式下不 panic
// 通过 peeksize 检查 receiver 是否有数据
if let Ok(size) = receiver_guard.peeksize() {
    // ...
}
// 验证至少收到了一些数据
if let Ok(recv_data) = recv_result {
    // ...
}
```

如果 `recv()` 返回 `Err(QueueEmpty)` 或者任何其他错误，整个测试会无 assertion failure 地通过，这会导致**虚假绿色**。

**建议修复**：
1. 将 `peeksize` 检查和 `recv` 断言拆开，明确要求 recv 成功：
   ```rust
   // 循环驱动直到收到数据或超时
   let recv_result = receiver_guard.recv();
   assert!(recv_result.is_ok(), "流模式下大数据 recv 应成功: {:?}", recv_result.err());
   let recv_data = recv_result.unwrap();
   assert!(!recv_data.is_empty(), "应收到非空数据");
   assert_eq!(&big_msg[..recv_data.len()], &recv_data[..], "数据内容应一致");
   ```
2. 或者增加重试驱动逻辑，确保数据已交付。

## 3. 中等问题 (Medium)

### [M1] 流模式下 `send()` 创建 segment 时使用 `current_millis()` 而非 `self.current`

**文件**：`src/core/kcp.rs:414`  
**严重等级**：**MEDIUM**

在 `send()` 方法的分片循环中，创建 `KcpPacketHeader` 时使用了 `current_millis()`（系统真实时钟）而不是 `self.current`（KCP 内部时钟）：

```rust
let header = KcpPacketHeader::new(
    self.conv,
    crate::KcpCmd::Push,
    frg,
    self.rcv_wnd,
    current_millis(),  // <-- 应该使用 self.current
    self.snd_nxt,
    self.snd_una,
    size as u32,
);
```

而 flush 方法中将 segment 从 `snd_queue` 移入 `snd_buf` 时会覆写 `ts` 字段：

```rust
seg.kcp_packet.header.ts = self.current;
```

所以这个 timestamp 不一致在 **正常 flow 中会被覆盖**，因而不是功能性 bug。但存在以下问题：

1. **设计一致性**：send 中应该使用 `self.current`，与 flush 保持一致。
2. **如果不经 flush 被调用方直接发送**（非标准用法，但可能有人在实现中用到），RTT 计算会使用真实时钟而非 KCP 内部时钟，导致 RTT 估计偏差。

**影响范围**：当前代码中 send 创建的 segment 在 flush 时会被覆盖 ts，所以当前路径无害。但代码风格不一致，可能误导后续开发者。

**建议修复**：将 `current_millis()` 改为 `self.current`，或使用 `let now = if self.current > 0 { self.current } else { current_millis() }`。

> **注**：此问题在实施前的代码中就已存在，不是本次流模式实现引入的。但作为本次审查的一部分，应该记录。

### [M2] 流模式与非流模式互连测试缺失

**文件**：`src/core/kcp.rs`  
**严重等级**：**MEDIUM**

设计评审（问题 12）明确确定了**流模式与非流模式不能互连互通**，并在实施计划的注意事项中强调"两端的 stream_mode 必须一致"。

但测试模块中缺少一个明确的**互连失败验证测试**，证明一端使用流模式、另一端不使用时的行为符合预期（数据丢失/错误）。实施计划步骤 7 中列为可选（`test_stream_mode_interop_fail` 可选），但考虑到这是一个关键设计约束，没有测试覆盖会增加回归风险。

**影响**：如果有人意外混用了两种模式，不会有测试提醒他们。

**建议修复**：添加一个测试用例，流模式 sender + 非流模式 receiver，验证 recv 的结果与预期不同（数据丢失或错误）。

## 4. 低优先级问题 (Low)

### [L1] `test_non_stream_mode_frg_limit` 中 MSS 计算与 `div_ceil` 语义不一致

**文件**：`src/core/kcp.rs:1242-1253`  
**严重等级**：**LOW**

```rust
let mss = kcp.mss as usize;
let big_data = random_bytes(mss * 300);
```

`send()` 内部使用 `buffer.len().div_ceil(self.mss as usize)` 计算分片数量。对于刚好等于 `mss * 300` 的数据，`div_ceil` 会得到恰好 300 个分片（因为能整除）。这是正确的。

但如果数据长度为 `mss * 255 + 1`（需要 256 个分片），非流模式应该**同样报错**，因为 256 > 255。当前的测试只用了 `mss * 300` 一个用例，边界覆盖不完整。

**影响**：极低，主要是边界测试覆盖不全。

### [L2] `test_stream_mode_peeksize_single_segment` 构造测试数据时未设置 `sn` 连续性

**文件**：`src/core/kcp.rs:1170-1183`  
**严重等级**：**LOW**

测试直接将 segment 推入 `rcv_queue`，跳过了 `input()` 中 sn 检查。虽然这个测试只测试 peeksize 行为，不测试数据流，但所有测试 segment 的 sn 设置为从 1 开始的递增序列，与其他测试不一致：

测试 1 (peeksize_single): sn=1  
测试 2 (peeksize_multi): sn=1, sn=2  
测试 3 (recv_single): sn=1  
测试 4 (recv_multi): sn=1, sn=2, sn=3

这些是合理的，但缺少文档说明这些测试仅覆盖 peeksize/recv 的逻辑而非网络数据流。

**建议**：无功能性影响，但可以为这些纯逻辑测试添加注释，说明它们绕过 input() 直接操作队列。

### [L3] `stream_mode` 在 `KcpConfig` 的 struct 文档注释中缺少对新加字段的提及

**文件**：`src/config/params.rs`  
**严重等级**：**LOW**

`KcpConfig` 的 rustdoc 注释没有更新以提及 `stream_mode` 字段。虽然新增字段有独立的 doc comment，但 struct 级别的文档仍然只列出 mtu/interval/nodelay/fastresend/nocwnd/snd_wnd/rcv_wnd。

**影响**：生成的 API 文档中，`KcpConfig` 的概要描述不完整。
