## 🔴 严重问题

### C-1: `flush()` 中 `need_wask` 的计算顺序错误

**文件**: `src/core/kcp.rs`，第 431-433 行

```rust
let acks_to_send = self.acklist.clone();
self.acklist.clear();                              // ← 先 clear
let need_wask = self.acklist.is_empty() && ...;     // ← 永远为 true（刚 clear）
```

**问题描述**:  
`need_wask` 的条件要求 `acklist.is_empty()`，但此处 **先 `clear()` 再判断**，导致 `acklist.is_empty()` 永远为 `true`。  
- 当 `probe & IKCP_ASK_SEND != 0` 时，`need_wask = true` 是正确的。  
- 但当 `probe & IKCP_ASK_SEND == 0` 时，`need_wask = false` 也是正确的（因为 `false && ... = false`）。  

**实际影响**:  
虽然在这个具体上下文中 `need_wask` 碰巧能得到正确值（因为 `acklist` 已空、只有 `probe` 决定结果），但这是**逻辑错误**——代码意图是判断"如果没有 ACK 需要发送且需要窗口探测"，而不是"acklist 为空（但刚清空）"。在维护中如果有人在 `clear()` 和这段之间的插入代码，就会引入 bug。

**修复建议**:  
将 `need_wask` 的计算移到 `clear()` 之前，与 `acklist` 的克隆同时完成：

```rust
let acks_to_send = self.acklist.clone();
let need_wask = self.acklist.is_empty() && (self.probe & IKCP_ASK_SEND) != 0;
let need_wins = (self.probe & IKCP_ASK_TELL) != 0;
self.acklist.clear();
```

### C-2: `parse_ack()` 中 RTT 计算的 `sn` 匹配条件错误

**文件**: `src/core/kcp.rs`，第 324 行

```rust
for seg in self.snd_buf.iter() {
    if self.timediff_u32(sn, seg.kcp_packet.header.sn) >= 0 {
```

**问题描述**:  
RTT 计算时，只要 `sn >= seg.sn`（即 ACK 确认的 sn 大于等于段 sn）就更新 RTT。正确逻辑应该是**精确匹配** `sn == seg.sn`。  

在原始 C 代码 `ikcp_parse_ack` 中：
```c
// 原版匹配的是 ==
if (sn == seg->sn) { ... break; }
```

当前代码使用 `>=` 会导致：  
- 如果发送端发送了多个段（sn=1, 2, 3），收到对 sn=3 的 ACK，却可能匹配 sn=1 的段来计算 RTT，导致 RTT 估计严重偏低。  
- 这会进一步导致 `rx_rto` 偏低，增加超时重传的误判率。  

该 bug **并非流模式引入**，而是此次提交中 `parse_ack` 的代码被压缩时引入的新 bug（原代码中该项逻辑正确）。

**修复建议**:  
将 `>=` 改为 `==`：

```rust
if seg.kcp_packet.header.sn == sn {
```

## 🟡 中等问题

### M-1: `send_control(Wask, 0)` 的 sn 参数语义不明确

**文件**: `src/core/kcp.rs`，第 402-406 行、第 438 行

```rust
// send_control 定义
async fn send_control(&mut self, cmd: KcpCmd, sn: u32) -> KcpResult<()> {
    self.send_packet(KcpPacket::new_without_data(KcpPacketHeader::new(
        self.conv, cmd, 0, self.rcv_wnd, current_millis(), sn, self.rcv_nxt, 0,
    ))).await
}

// 调用处
self.send_control(KcpCmd::Wask, 0).await?;
```

**问题描述**:  
WASK 包的协议设计通常将 sn 字段设为 0，这是合理的。但该方法将 sn 统一设为参数传入值，而在 `flush` 中为 `Ack` 调用时传递实际 sn，这很好。问题不在功能层面，而在于：

当 `need_wask = false` 时，所有 ACK 会被发送；但当 `need_wask = true` 时，这些 ACK 被**丢弃**（`acks_to_send` 被克隆后未使用）。根据原始 C 代码逻辑，WASK 包应**替代** ACK 包的发送，而非简单地丢弃 ACK。原始逻辑使用了 `resend = ackcount` 的方式复用 acklist 空间。

**实际影响**:  
在需要发送 WASK 时，所有已记录的 ACK 都丢失了，可能导致对端收到不必要的重复数据或窗口停滞。

**修复建议**:  
当 `need_wask` 为 true 时，在发送 WASK 之后仍应发送 ACK 包。将 `else` 改为独立判断：

```rust
if need_wask {
    self.send_control(KcpCmd::Wask, 0).await?;
}
for sn in acks_to_send {
    self.send_control(KcpCmd::Ack, sn).await?;
}
```

### M-2: `flush()` 中对 `self.ts_lastack` 的更新缺失

**文件**: `src/core/kcp.rs`，第 501 行附近

```rust
} else if self.timediff_u64(current, self.ts_lastack) >= 0 {
```

**问题描述**:  
`ts_lastack` 在整个代码中从未被赋值（始终保持 0），但 `flush` 中用它来判断是否更新拥塞窗口。`current` 始终 >= 0（因为 ts_lastack=0），所以拥塞窗口递增逻辑无论是否收到 ACK 都会执行。

在原始 C 代码中，`ts_lastack` 在 `parse_ack()` 中被更新为当前时间，只有当收到 ACK 后才增加拥塞窗口。当前代码相当于**永远认为有 ACK 确认**，拥塞窗口增长过快。

这不是流模式的问题，但在此次代码修改中被引入（原实现有正常的 `ts_lastack` 更新逻辑）。

**修复建议**:  
在 `parse_ack` 中找到匹配 ACK 后，更新 `self.ts_lastack = current`：

```rust
if seg.kcp_packet.header.sn == sn {
    let rtt = self.timediff_u64(current, seg.kcp_packet.header.ts);
    if rtt >= 0 {
        // ... RTT 更新 ...
        self.ts_lastack = current;  // ← 新增
    }
    break;
}
```

### L-2: `parse_data` 中的插入逻辑使用低效的 tail 弹出模式

**文件**: `src/core/kcp.rs`，第 384-394 行

```rust
let mut tail = Vec::new();
for _ in insert_pos..self.rcv_buf.len() {
    tail.push(self.rcv_buf.pop_back().unwrap());
}
self.rcv_buf.push_back(newseg);
for seg in tail.into_iter().rev() {
    self.rcv_buf.push_back(seg);
}
```

**问题描述**:  
为了在双端队列中间插入一个元素，先将插入点后的所有元素弹出到临时 Vec，再推入新元素，再反向推回这些元素。复杂度 O(n)，且涉及额外分配。

虽然 `KcpDeque` 是双端队列，不直接支持中间插入，但该逻辑是原代码就有的，此次改动用 `pop_back` + `into_iter().rev()` 替代了原 `pop`（从尾部弹出），行为等效但不够直观。

**建议**:  
可考虑在 `KcpDeque` 上实现一个 `insert_at` 方法，或保留原实现。

### L-4: `test_stream_mode_full_cycle_small` 测试中 `current_millis()` 的使用

**文件**: `src/core/kcp.rs`，第 644 行

```rust
let now = current_millis();
s.current = now;
r.lock().unwrap().current = now;
```

**问题描述**:  
测试中使用真实的 `current_millis()` 作为初始时间，然后硬编码 `now + 20` 作为 update 时间。在 `nodelay=true, interval=20` 的配置下，`ts_flush = interval = 20`。

真实毫秒值通常在 10^13 量级（unix 毫秒），第一次 `ts_flush` 被设为 `current`（大值），然后 `ts_flush = current + interval`。在时间差计算 `timediff_u64(now+20, ts_flush)` 时，`ts_flush > now+20`（因为初始 `ts_flush` 被设为了 `current` 而非 `current + interval`），所以 `now + 20` 不会触发 update。

等一下——让我重新检查：`update()` 中 `ts_flush` 初始化为 `interval`（20），然后 `update(now+20)` 时 `timediff(now+20, 20) >= 0` 成立，会执行 flush。

但是 `current` 字段被覆盖为 `now`（大值），而 `ts_flush = config.interval = 20`（小值），所以 `timediff_u64(self.current, self.ts_flush) = timediff_u64(now, 20) >= 0`。这逻辑上是正确的但时间戳不一致，可能导致 future 测试中的微妙 bug。

**建议**:  
使用固定的小时间值（如 `1000`）代替 `current_millis()` 进行单元测试，避免依赖系统时钟。

## 最终建议

1. **优先修复 C-1 和 C-2**：两处都是严重逻辑 bug，C-2 会影响非流模式下的 RTT/RTO 估计。
2. **修复 M-1**：ACK 被 WASK 替代发送，可能导致数据包不必要的重传。
3. **恢复文档注释**（L-1）：为公共结构和方法添加文档注释，提升可维护性。
4. 流模式的核心功能测试（35 个全通过）覆盖了：
   - 单个/多个 segment 的 peeksize
   - 单个/多个 segment 的 recv
   - 空队列错误
   - 255 分片限制解除
   - 非流模式 frg 递减验证
   - 完整 send-update-input-recv 链路
   - 连续多次 send + recv
